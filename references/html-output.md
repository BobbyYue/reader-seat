# Self-Contained HTML Rendering

Use this module only after
[format-decision.md](format-decision.md) selects HTML explicitly, by inherited
target, or by default. It defines the self-contained HTML rendering layer and
has no dependency on a separately installed HTML-report skill.

Reader's Seat still owns the reader task, source boundary, scenario structure,
title, evidence, language, and portable presentation baseline. This module owns
HTML file layout, local runtime assets, responsive behavior, and browser
verification.

## Output Contract

This section and the remaining HTML mechanics apply only when the selected
format is HTML.

Deliver one portable directory:

```text
<report-name>/
|-- <report-name>.html
|-- assets/
`-- _shared/
    |-- fonts/
    |-- js/
    `-- licenses/
```

- The HTML and every required asset must work from local relative paths.
- Do not require a web server when plain local HTML can provide the requested
  behavior.
- Do not use CDN scripts, remote fonts, absolute local paths, `file://` asset
  references, or base64-encoded files.
- External source URLs are allowed as clickable evidence links.
- Copy only the optional runtime libraries actually used by the artifact.
- The first line of every generated HTML file must be
  `<!-- Generated by Reader's Seat -->`.
- Do not expose Reader's Seat, its gates, prompts, or validation process in the
  visible document.

## Plan Before Building

For every HTML task, decide these items internally before authoring:

1. artifact type, target reader, reader task, and chosen output language;
2. content structure from the selected Reader's Seat scenario;
3. visual personality appropriate to the domain and audience;
4. page width, reading width, mobile collapse behavior, and print behavior;
5. palette variables, type hierarchy, table treatment, callouts, and figures;
6. planned visuals, their reader jobs, deletion-test results, and the factual claim each visual may imply;
7. citation inventory and source-to-claim mapping;
8. verification viewports and any interaction states that need testing.

Create a `plan.md` beside the report when the document has at least five
substantive sections, multiple visuals, or interactions whose consistency would
otherwise be difficult to track. The plan is an authoring aid, not part of the
reader-visible document.

## Scaffold

Use the bundled script from the Reader's Seat directory:

```bash
bash <reader-seat-dir>/scripts/new-html-report.sh <report-name> <output-dir> --lang <locked-output-language>
```

Add optional local libraries only when the report uses them:

```bash
bash <reader-seat-dir>/scripts/new-html-report.sh <report-name> <output-dir> --lang <locked-output-language> --charts
bash <reader-seat-dir>/scripts/new-html-report.sh <report-name> <output-dir> --lang <locked-output-language> --diagrams
bash <reader-seat-dir>/scripts/new-html-report.sh <report-name> <output-dir> --lang <locked-output-language> --charts --diagrams
```

On native Windows:

```powershell
pwsh -File <reader-seat-dir>/scripts/new-html-report.ps1 <report-name> <output-dir> -Language <locked-output-language> -Charts -Diagrams
```

The scaffold requires the runtime contract's locked output language and writes
it into the HTML `lang` attribute. It copies the bundled Work Sans and Red Hat Mono fonts automatically.
It copies ECharts for `--charts` and Mermaid for `--diagrams`. Author directly
inside the created directory; there is no separate deployment step. Keep the
copied `_shared/licenses/` directory with the artifact when redistributing it.

## Visual System

Apply [visual-decision.md](visual-decision.md) before selecting a chart,
diagram, table, screenshot, callout, card group, or semantic color. Record the
reader question, prose alternative, decision state, and deletion result. If a
material visual is retained, load
[visual-communication.md](visual-communication.md) before implementation. The
rules below govern the HTML implementation of the resulting decision.

- Let the document's subject determine the visual personality. Do not use one
  fixed Reader's Seat theme for every report.
- Default to restrained solid surfaces, clear rules, generous whitespace, and
  a palette with functional contrast. Avoid decorative gradients, floating
  section cards, nested cards, or one-note color themes unless the user's
  existing design system requires them.
- Define all colors and font families in `:root`; use variables throughout the
  remaining CSS.
- Use one body family and one mono family by default. Create hierarchy with
  size, weight, spacing, and layout rather than a collection of display fonts.
- Use content-bearing headings from the Reader's Seat heading proposition map.
  Do not add generic HTML-report labels such as `Key insight`, `Why it matters`,
  or `30-second summary`.
- Keep cards for repeated items or genuinely bounded tools. Use unframed
  sections or full-width bands for the document's main argument.
- Every figure must have a visible, content-specific title or caption. Captions
  and nearby labels must preserve the visual evidence decision from
  [visual-evidence.md](visual-evidence.md).
- Do not create a visual merely to satisfy a layout. Prefer a table, diagram, or
  chart only when it reduces comparison or reasoning effort.

## Citations And Sources

When material claims use searched or supplied evidence, cite them next to the
claim:

```html
<sup><a href="#cite-1">[1]</a></sup>
```

Use a matching ordered source list:

```html
<footer>
  <div class="sources">
    <h2>Sources</h2>
    <ol>
      <li id="cite-1">
        <span class="src-title">Author or organization, source title and context.</span>
        <a class="src-url" href="https://example.com/source"
           target="_blank" rel="noopener noreferrer">Open source</a>
      </li>
    </ol>
  </div>
</footer>
```

- Number sources sequentially from 1.
- Every inline citation must resolve to one source entry.
- Every source entry must support at least one material statement.
- Use clickable direct source URLs, not search-result URLs.
- Long source links must wrap without expanding the page.
- For a user-supplied local source without a URL, identify it as a user-supplied
  source without fabricating a link.

## Charts And Diagrams

### Quantitative Charts

When a chart is necessary, use the bundled ECharts runtime copied by
`--charts`.

Use [visual-communication.md](visual-communication.md) for chart choice,
geometry, scale, labels, color semantics, context, and hard failures. The rules
below are HTML runtime requirements.

- Reference `./_shared/js/echarts.min.js` before the report-local chart script.
- Put chart configuration in `assets/charts.js`, not an inline script.
- Use the SVG renderer, disable animation, and resize on viewport changes.
- Read chart colors from the report's CSS variables; do not use the library's
  default rainbow palette.
- Include units, denominators, periods, comparison bases, zero baselines where
  relevant, missing-data treatment, and uncertainty. Quantitative bars require
  a zero baseline.
- Do not chart values that are absent from or exceed the source evidence.

### Structural Diagrams

Use ordinary HTML and CSS for a simple flow. Use the bundled Mermaid runtime
copied by `--diagrams` when the structure has enough nodes or relationships to
justify it.

- Reference `./_shared/js/mermaid.min.js` locally.
- Give every diagram a visible title and bounded caption.
- Label a diagram as a proposal or synthesis when it is not copied from the
  source.
- Do not present a conceptual diagram as proof that a real system has been
  implemented.

## Responsive, Accessible, And Print-Safe Output

- Use a stable max-width and responsive constraints for every fixed-format
  element.
- Keep normal body text at least 14px and use readable line height.
- Maintain WCAG AA contrast for substantive text and controls.
- Do not communicate status by color alone.
- Wrap every table in `.table-wrap` with horizontal scrolling. A table with
  four or more columns must use the full content width rather than sit inside a
  multi-column grid.
- Collapse multi-column layouts at an intentional breakpoint. Do not scale text
  with viewport width.
- Ensure long terms, URLs, code, headings, and buttons fit on a 390px viewport.
- Provide keyboard focus states for links and controls.
- Add print styles that remove nonessential interaction, preserve contrast, and
  avoid splitting tightly related figures or callouts when practical.

## Verification

Run the bundled static validator:

```bash
python3 <reader-seat-dir>/scripts/validate_html_output.py <report-file.html>
```

Then open the actual file in a browser and verify at least:

1. desktop around 1440px wide;
2. mobile around 390px wide;
3. fonts and all local assets load;
4. body scroll width does not exceed the viewport;
5. tables and code scroll only inside their intended containers;
6. title, first-screen conclusion, headings, labels, and captions do not
   overlap or truncate;
7. source links, citation jumps, navigation, charts, and interactions work;
8. the final visible artifact contains no scaffold placeholders.

For an interactive report, also test keyboard access, empty/error states, and
the primary workflow. A loading file is not enough to claim verification.

## Acceptance Questions

- Did an explicit or inherited target format override the HTML default?
- If the target is not HTML, does it preserve native platform behavior while
  carrying over the portable hierarchy and visual principles?
- Can the target reader understand the main result and document path without
  knowing how the HTML was generated?
- Does every visual and structural element reduce reading or comparison effort?
- Can every material claim be traced to evidence without leaving the artifact
  in a broken state?
- Does the artifact work after the separate HTML-report skill is removed or was
  never installed?
- Is the delivered directory portable, locally renderable, responsive, and
  free of unresolved asset paths?
