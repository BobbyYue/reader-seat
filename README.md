# Reader's Seat

> 让 AI 站到读者的位置，把工作材料写成更容易理解、判断和行动的文档。

Reader's Seat 是面向 Codex 和其他 AI Agent 的读者优先写作 Skill（reader-first AI writing skill）。它用于整理新闻资讯、技术方案、产品文档、业务汇报、数据分析报告和 SOP，在保留事实与证据边界的同时，让真正的结论、判断依据和下一步更容易找到。

## 一图看懂

```mermaid
flowchart LR
    A[原始材料] --> B[识别读者与任务]
    B --> C[保留事实与证据边界]
    C --> D[重组结论、依据与行动]
    D --> E[输出易读的目标文档]
```

你提供材料、读者、目标和格式；Reader's Seat 负责选择合适的结构、解释深度与视觉形式。它不会为了让内容显得完整而补造事实，也不会强迫所有文档使用同一套模板。

## 它解决什么问题

很多 AI 文档语句通顺，但读完仍然不知道：结论是什么、证据在哪里、哪些只是推测、接下来要做什么。

Reader's Seat 适合在你已经有材料，或者需要基于可靠来源起草文档时使用。它会优先帮助读者：

- 尽快找到真正需要知道的结论；
- 看清数字、证据、判断和未知之间的关系；
- 理解这件事意味着什么，以及是否需要行动；
- 在不改变事实、立场和承诺的前提下，减少 AI 味、空话和形式化表达；
- 只在图表、表格或颜色确实降低理解成本时使用视觉表达。

它不是一套固定文章模板。同一份材料，会根据读者真正要完成的任务，选择不同的结构、标题、解释深度和视觉形式。

## 适合哪些工作文档

| 你手里的材料 | Reader's Seat 重点处理什么 |
| --- | --- |
| 新闻、访谈、行业资料 | 区分已确认信息、消息来源、时间和未知，不用悬念标题代替内容 |
| 技术方案、架构评审 | 让约束、选项、取舍、风险、回滚和决策条件容易比较 |
| 产品介绍、发布说明、PRD | 说清楚给谁用、解决什么问题、能做什么、暂时不能做什么 |
| 项目汇报、复盘、绩效总结 | 区分活动、交付和结果，让进展、影响、风险和下一步容易判断 |
| 数据分析、研究报告 | 保留指标口径、幅度、证据和因果边界，把缺口对应到下一步验证 |
| SOP、帮助文档、运行手册 | 补齐前置条件、步骤、成功信号、异常分支、恢复和升级路径 |

短消息润色、纯视觉美化和没有材料依据的内容扩写，不是它的主要用途。

## 3 分钟开始使用

### 在 Codex 中安装

```bash
git clone https://github.com/BobbyYue/reader-seat.git ~/.codex/skills/reader-seat
```

重新打开一个 Codex 任务后，可以显式调用：

```text
使用 $reader-seat 重写这份项目复盘。
读者是不了解项目细节的管理者，希望他能判断进展、影响、风险和下一步。
保留原有事实和数据，输出为飞书文档结构。
```

也可以直接使用自然语言：

```text
请从读者视角重构这份技术方案，让第一次接触项目的评审者能看懂约束、选项和取舍。
```

### 在其他 Agent 中使用

将仓库放到该 Agent 可读取的位置，并让它显式加载 `SKILL.md`。不同 Agent 的自动发现方式并不相同；第一次使用时，显式加载比依赖自动触发更可靠。

需要验证不同 Agent 是否执行了同一套规则时，参考 [跨 Agent 使用与评测](references/agent-portability.md)。仓库同时支持无头命令 Agent 和需要人工导入、导出结果的 GUI Agent。

## 你需要告诉它什么

多数情况下只需要四项信息：

```text
材料：需要处理的原文、数据或来源
读者：谁会阅读，对业务熟悉到什么程度
目标：读者看完需要理解、判断或完成什么
格式：HTML、飞书、Word、Markdown、纯文本等；不写则默认 HTML
```

不必为了使用 skill 写一份复杂提示词。缺少的信息不会实质改变结构或结论时，Reader's Seat 会采用保守假设；如果缺口会改变事实、判断强度或行动，它才会要求补充。

## 直接可用的提示词

### 工作汇报

```text
使用 $reader-seat 整理这份半年工作材料。读者是管理者。
请区分做了什么、交付了什么、产生了什么结果；没有影响数据的地方不要替我包装成业务价值。
```

### 数据分析

```text
使用 $reader-seat 重写这段分析结论。
保留指标、方向、幅度和时间范围，区分观察到的现象、可能解释、因果判断和未知，并给出与证据缺口匹配的验证方向。
```

### 技术方案

```text
使用 $reader-seat 诊断这份技术方案是否足以进入评审。
读者需要比较约束、备选方案、取舍、迁移风险和回滚条件。只指出缺口，不替作者编造方案。
```

更多示例见 [examples/quick-start.md](examples/quick-start.md)。

## 输出时会遵循什么

### 事实优先于表达效果

不会为了让文字更有说服力，新增来源、数字、原因、结论、负责人、截止时间或确定性。观察、解释、因果、建议和未知会保持可区分。

### 标题必须提供信息

标题应说明具体对象和正文能够兑现的核心关系、变化或结论。不会使用“真正的原因”“最值得带走”“一文看懂”等只制造阅读期待、却没有提供内容的表达。

### 视觉必须降低读者成本

图表、表格、卡片、颜色和截图不是必选项。Reader's Seat 会先比较简短文字是否已经足够；只有视觉能让读者更快定位、比较、理解或验证时才保留。

### 格式服从使用场景

- 明确指定飞书、Word、Markdown、纯文本或其他格式时，保留目标平台的原生能力。
- 编辑已有文档时，默认保持原格式。
- 没有指定格式的新文档，默认生成自包含 HTML。
- 没有指定输出语言时，默认沿用原材料的主要语言，而不是提示词的语言。

## 一个简短例子

原始材料：

```text
版本发布当周，7日留存从42%降到38%。目前只有按周汇总数据，
没有实验、用户分层或同期外部因素数据。
```

Reader's Seat 会保留“下降 4 个百分点”，但不会写成“版本导致留存下降”：

```text
版本发布当周，7日留存从42%降到38%，下降4个百分点。
当前只能确认留存下滑，不能判断是否由版本发布导致；
下一步需要补充分层和对照信息后再验证归因。
```

## 使用边界

- Reader's Seat 不会自行发布、覆盖原文或替你发送内容。
- 来源不足时，它会缩小结论或明确缺口，不会把薄材料写成完整事实。
- 视觉来源不明时，它会改用概念图或无图，不会把搜索结果中的人物照片当作已核验事实。
- 不同 Agent 的措辞和排版可能不同；需要稳定的是事实、证据边界、场景选择、语言、格式和行动边界。

## 当前验证状态

- 6 类工作文档场景和 8 项通用输出标准均有结构校验。
- Codex 当前测试中，同一高风险分析案例连续运行 3 次，并对每份结果进行 2 次自动语义评审，全部通过硬门。
- 仓库提供跨 Agent 冻结案例和矩阵评测，但在至少两个明确命名的 Agent 完成同案例测试前，不声称跨 Agent 已稳定。

这些测试用于建立质量下限，不意味着任何模型在所有材料上都不会出错。重要文档仍应由责任人确认事实、判断和授权边界。
